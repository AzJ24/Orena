# 2026-07-29 — SEGMENT track: pipeline built, and a 4× training speedup

First day on the **SEGMENT** track (video clips, up to 5 min) with
**Qwen3.6-27B**. Built the whole pipeline end to end, then spent most of the day
on a performance problem that turned out to be a missing kernel package, not
anything in our code. Everything below is measured, not estimated.

Plan and rationale live in [../segment_track/plan.md](../segment_track/plan.md).

---

## 1. What the track is, and why it isn't just "frame with more pixels"

| | FRAME (done earlier) | SEGMENT (this) |
|---|---|---|
| input | 1 JPEG | N frames from `[start, end]` |
| clip length | 0 s | 29 s / 119 s / 299 s (three fixed lengths) |
| biggest bucket | `fo_class` 46% | **`time` 38.6%** — absolute `hh:mm:ss` |
| new format | — | `percentage` (39 rows) |
| latency budget | 5 s | **15 s** |
| model | Qwen3.5-9B | Qwen3.6-27B (27.4B params) |

The hard part is `time`: the answer is an absolute timestamp in the source video
(e.g. `01:09:58`) but the model only sees a clip window.

## 2. The `time` problem is solved by the processor itself

`Qwen3VLProcessor` interleaves a timestamp marker before every frame, computed
from the `VideoMetadata` we pass:

```
<557.4 seconds><|vision_start|>[…220 video tokens…]<|vision_end|>
<576.7 seconds><|vision_start|>[…]<|vision_end|>   … 40 of these
```

Pass `frames_indices` as **absolute** indices into the source video plus the real
`fps`, and those markers are absolute video time — exactly the frame of reference
the answers use. No burned-in overlay needed.

**Probe on the untuned base model** (before any training) confirmed it works:

| ground truth | prediction |
|---|---|
| `02:36:13` | `02:36:14` — 1 s off |
| `00:18:49` | `00:18:50` — 1 s off |

So the model reads the markers *and* converts seconds → `hh:mm:ss` correctly.
The feared divmod-arithmetic failure doesn't happen. **Decision: markers only;
the `frames_overlay/` burned-in-clock arm was dropped.**

### Three traps, all found on CPU before any GPU time

1. **`do_sample_frames=False` is mandatory.** By default the video processor
   *re-samples* the frames you already sampled, using indices derived from
   `total_num_frames`. Raises `IndexError` in one configuration and *silently
   overwrites* `frames_indices` in another.
2. **`VideoMetadata` must carry real `fps` + absolute indices.** Omit them and it
   warns once, assumes `fps=24`, and renders `<0.0 seconds> … <1.3 seconds>` — a
   5-minute clip described as 1.3 seconds. Training proceeds and produces garbage.
3. **Anchors are N/2, not N.** `temporal_patch_size=2` fuses frames in pairs, so
   80 frames give **40** timestamp markers. This halves the temporal resolution
   you think you have, and it drove the N sizing below.

## 3. Choosing N — the tolerance is clip-dependent

From `orena-focus` (the official package), tolerance is set per clip:

```python
threshold_seconds = min(5.0, 1 + duration * (4 / 360))
```

Our data has exactly three clip lengths, so three tolerances. Worst-case
timestamp error is **half the anchor spacing**, so the requirement is
`spacing/2 ≤ tolerance`:

| clip | tolerance | N=64 | N=72 | **N=80** |
|---|---|---|---|---|
| 29 s | 1.32 s | 0.47 ✅ | 0.41 ✅ | 0.37 ✅ |
| 119 s | 2.32 s | 1.92 ✅ | 1.70 ✅ | 1.53 ✅ |
| **299 s** | **4.32 s** | **4.82 ❌** | 4.27 ✅ *(1.2% margin)* | **3.83 ✅ *(11%)*** |

Only the 299 s clips (13% of the time bucket) ever fail. **N=80 chosen** — N=72
satisfies it on paper by ~50 ms, which is inside rounding noise.

## 4. The performance problem — 8% MFU

First real timing run: **261 s per optimizer step → 28 h/epoch → 84 h for 3
epochs.** Not feasible. Profiling found:

| component | time |
|---|---|
| vision tower (64 frames) | **0.11 s** — ruled out |
| forward | 3.50 s |
| **backward + recompute** | **13.44 s** |

The kernel table gave it away — read the *call counts*:

| kernel | time | calls | avg |
|---|---|---|---|
| `aten::add_` | 4.63 s (31%) | **89,073** | 52 µs |
| `aten::copy_` | 2.36 s | **143,849** | 16 µs |
| `aten::mm` *(real work)* | 2.27 s | 3,538 | 642 µs |
| `aten::bmm` | 1.07 s | **122,305** | **8.8 µs** |

**CPU dispatch 21.5 s > GPU compute 14.9 s.** The GPU was idle waiting for Python
to launch ~580,000 microscopic kernels per step.

**Root cause:** Qwen3.5/3.6 is a 3:1 hybrid — **48 of 64 layers are Gated DeltaNet
(linear attention)**. Those need fused kernels from `flash-linear-attention`.
Without it transformers silently substitutes `torch_chunk_gated_delta_rule`, a
Python chunked loop. The startup warning says so; it's easy to miss.

## 5. Fixing it took three separate blockers

1. **Python 3.13 has no working `fla` build.** The PyPI wheel installs a broken
   namespace package — and because transformers imports `fla.modules`
   unconditionally once `fla` is importable, it *breaks the model class* rather
   than degrading. ms-swift's guide says plainly: use Python 3.12.
2. **`/usr/bin/python3.12` ships no `Python.h`.** Triton JIT-compiles a C
   extension at runtime, so kernels failed to build. uv-managed interpreters
   bundle headers; the system one doesn't.
3. **Triton 3.7.0 computes wrong gradients on Hopper.** `fla` *refuses to run*:
   `Triton >= 3.4.0 and < 3.7.1 on Hopper GPUs produces incorrect results for
   gated chunk_bwd_dqkwg`. Bumping to 3.7.1 cleared it. Had fla not guarded this,
   we'd have trained on corrupt gradients and never known.

**Result — `venv3.12`**, built with uv on a managed CPython 3.12.13, an exact
clone of `.venv`'s 207 pinned versions plus `fla` and Triton 3.7.1:

| | before | after |
|---|---|---|
| step time (N=64) | 261 s | **66 s** |
| MFU | 8% | **33%** |
| per epoch | 28.1 h | **7.1 h** |

`.venv` is untouched. `causal_conv1d` is still absent (needs `nvcc`); the source
shows the fallbacks are independent, so the expensive half is fixed — only the
cosmetic "fast path not available" warning remains.

## 6. Tuning that did *not* help (and why)

- **Batch size.** Before the fix, batch 2 was 14% faster; after, it's **7%
  slower** (71 s vs 66 s) and costs 8 GB. The earlier gain was never a batching
  win — it was amortizing dispatch overhead we were drowning in. **Batch 1 stays.**
- **Dropping gradient checkpointing.** OOMs on both GPUs at 139.8 GB. `fla` is
  only ~2 GB leaner than the fallback. **Required.**
- **Deduplicating overlapping clips.** 41% of rows share a (video, question,
  answer) triple, but sibling clips overlap only 24% — they're genuine
  augmentation, not redundancy.

## 7. Base-model baseline (Qwen3.6-27B, no training)

20 heico test clips, via the official `Evaluator` with `track=Track.SEGMENT`:

- **accuracy 30%** (6/20)
- **latency: median 5.12 s, max 13.85 s, 0 of 20 over the 15 s limit**
- **format compliance already perfect** — raw outputs are `'Clip'`, `'none'`,
  `'Sponge'`. The `direct` prompt works; nothing for `extract_answer` to salvage.

Note the Evaluator scores latency violations as **wrong answers**, not errors —
so a latency regression looks like an accuracy drop.

## 8. Final configuration

| | |
|---|---|
| data | heico + lapchole HF **train** splits, video-level 10% eval carve-out |
| | train 12,386 (83 videos) · eval 1,360 (9) · test 6,254 (38, untouched) |
| clip | **N=80** frames @ 640×360 → 40 anchors, 9,924 tokens/sample |
| model | Qwen3.6-27B, LoRA r=8 α=16 → 39.8M trainable (0.145%) |
| batch | 1 × accum 16 × 2 GPUs = **effective 32** |
| schedule | lr 1e-4, bf16, gradient checkpointing, ≤3 epochs |
| eval/save | every **50** steps; eval on **512 clips stratified by (video, format)** |
| early stop | patience 3 (150 steps), `load_best_model_at_end` |
| checkpoints | **all kept** — 464 MB each, ~23 ≈ 11 GB |
| projected | 25.8 h train + 4.8 h eval = **30.6 h** (2-day SLURM limit) |

The eval split is 1,360 clips but only **9 videos**, two of which contribute 400
clips each (59%). Stratifying the 512-clip subset over (video × format) cuts those
two to 29% and keeps all 7 formats including the 3 `percentage` clips. The subset
is fixed across evals, so the `eval_loss` curve carries no sampling noise.

## 10. Smaller findings

- **`qID` collides across datasets** (heico 60576 and lapchole 60576 are different
  questions; 3 rows). Added a qualified `uid`; kept raw `qID` since the Evaluator
  matches on it per dataset.
- **The prompt's own example looked like data.** `<559.8 seconds>` in the system
  prompt was indistinguishable from a real frame marker — changed to
  `<1234.5 seconds>`.
- **orena-focus 0.3.5** (upgraded from 0.3.4) changes exactly one thing:
  `Percentage.compare` now honours `threshold_pp` (±5 pp) instead of requiring an
  exact match. The `time` tolerance formula is **byte-identical**, so all the N
  analysis holds.
- **Installing anything can silently downgrade Triton to 3.7.0** — torch pins it.
  The trainer now has a startup guard that aborts on `fla` missing or Triton
  < 3.7.1.
- **Frame I/O is latency-bound, not bandwidth-bound**: 71 ms/frame cold over NFS
  (2 MB/s effective). 80 JPEGs/sample would be 36 s/step single-threaded, ~1 s
  across 32 CPUs — hidden entirely behind compute with 16–24 dataloader workers.
