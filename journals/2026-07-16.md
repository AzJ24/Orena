# 2026-07-16 — `build_frame_sft_dataset.py`

## What the script does

`scripts/build_frame_sft_dataset.py` builds a chat-formatted SFT dataset for
fine-tuning a VLM (target: Qwen 3.5 9B) on the FOCUS **frame track** —
questions answerable from a single still image.

Unlike `scripts/build_probing_dataset.py`, it does **not** read from the
`webapp/cache/qa_cache.parquet` cache. It loads the QA pairs itself, directly
via `focus.FocusDataset` (same as `data_exploration.ipynb`), pulling straight
from Hugging Face Hub (or its local offline cache).

Steps:
1. Load frame-track QA pairs for `train` and `test` splits from HF.
2. For each question, resolve the one frame JPEG it refers to — using the
   exact same path formula `FocusFrameDataset` uses internally
   (`round(start_time * base_fps)`), pointing at frames already extracted on
   disk under `<root_dir>/<dataset>/frames/`. Rows whose frame doesn't exist
   on disk are dropped and counted.
3. Split `train` into `train`/`eval` at the **video** level (not the question
   level, to avoid leaking correlated frames across the split), stratified by
   `procedure_type`, with a configurable `--eval-frac` (default 0.12).
4. Write three JSONL manifests (`train.jsonl`, `eval.jsonl`, `test.jsonl`).
   Each line is a chat-formatted record that **references** the existing
   frame's file path — it never copies or re-encodes image bytes, so the
   output stays at KB/MB scale instead of duplicating gigabytes of pixel data.

## Output (test run against `heico`, `--eval-frac 0.12`)

```
Loading 'heico' frame track from HuggingFace (train + test)...
  train: 8000 usable rows
  test:  4000 usable rows

Video-level eval split: 2 eval videos, 18 train videos (target eval_frac=0.12)
  final train: 7200 rows
  eval:        800 rows
  test:        4000 rows (untouched HF test split)
```

- All 8,000 train and 4,000 test frame-track rows resolved successfully (0
  dropped) — the pre-extracted frames on disk fully cover the QA benchmark.
- 2 of the 20 train videos (Proctocolectomy-stratified) were held out for
  eval, producing an 800/7,200 row split (~10% by row count, since videos
  contribute different numbers of frame-track questions).
- `test.jsonl`'s 4,000 rows are the official HF test split, left untouched as
  the final held-out benchmark — never used for eval during the SFT pipeline.

## Record format

Each JSONL line:

```json
{
  "qID": "8455",
  "videoID": "0009 - Heico - Prokto - 10.avi",
  "procedure_type": "Proctocolectomy",
  "primary_capability": "OBJECT_IDENTIFICATION",
  "secondary_capabilities": ["OBJECT_AGGREGATION"],
  "format": "fo_class",
  "messages": [
    {"role": "user", "content": [
      {"type": "image", "image": "/projects/datasets_ML/orena/heico/frames/0009 - Heico - Prokto - 10/frame0430775.jpg"},
      {"type": "text", "text": "Which combination of foreign object classes is visible in this frame? Please provide the class names or answer with none."}
    ]},
    {"role": "assistant", "content": [{"type": "text", "text": "Clip, Silicone loop"}]}
  ]
}
```

`messages` follows the conversation format most SFT frameworks (LLaMA-Factory,
ms-swift, trl) expect directly — image referenced by path, decoded lazily at
training time off local disk.

# `evaluate_qwen_frame.py`

*(Note: this script was actually written the following morning,
2026-07-17 — logged here since the session carried over. For bugs hit while
actually running it, and later additions like `predictions.jsonl`/timing

## What the script does

`orena_sft/evaluate_qwen_frame.py` evaluates a fine-tuned checkpoint from
`sft_train_qwen_frame.py` on the FOCUS frame-track **TEST** split, using the
FOCUS library's own built-in evaluation pipeline
(`focus.evaluation.Evaluator`) rather than a hand-rolled metric — the
library already implements exactly the split this project needed: closed-form
answer formats get deterministic parsing/comparison, open-ended ones get
routed to an LLM judge.

Unlike training (which reads `train.jsonl`/`eval.jsonl`), this script loads
`Request`/`Reference` objects **directly from `focus.FocusDataset`**, not
from `test.jsonl` — `Evaluator.run()` needs the library's typed dataclasses
(`Request`, `Reference`, `Response`), not raw JSON dicts. Frame paths are
resolved with the exact same `frame_path()` helper `build_frame_sft_dataset.py`
uses (imported directly from it, so both scripts stay consistent by
construction rather than by convention).

## Steps

1. **Load the model.** Auto-detects whether `--checkpoint-dir` holds a LoRA
   adapter (`adapter_config.json` present — the default output of training)
   or a full fine-tuned model, and loads accordingly. LoRA is merged into
   the base weights by default (`peft_model.merge_and_unload()`) for faster
   inference; `--no-merge-lora` keeps it as a separate adapter.
2. **Load ground truth.** For each `--datasets` entry (`heico`, `lapchole`,
   or both), loads `FocusDataset(dataset, DatasetSplit.TEST, Track.FRAME)` —
   the real typed `Request`/`Reference` objects, matching what training's
   `build_frame_sft_dataset.py` used to build `test.jsonl` in the first
   place, so results are directly attributable back to those exact rows.
3. **Generate.** For each test example, builds the same prompt shape used at
   training time (`processor.apply_chat_template(..., add_generation_prompt=True,
   enable_thinking=False)` — direct answer, no reasoning scaffold), runs
   greedy generation (`do_sample=False`) capped at `--max-new-tokens`
   (default 32, matching the training-time `SampleGenerationCallback`), and
   times each call into a `focus.data.data_models.Response(qID, content,
   latency)`.
4. **Score.** Hands `(requests, references, responses)` to
   `Evaluator.run()`:
   - `binary`, `number`, `percentage`, `fo_class`, `time` → deterministic
     `.read()` + `.compare()` per format class, no LLM involved.
   - `open_ended`, `matching`, `multiple_choice` → `TransformersJudge`
     (default `Qwen/Qwen3.5-4B`, `--judge-device cpu` by default since the
     main model already occupies the GPU), majority-voted if multiple
     judges are configured.
5. **Report.** Writes `results.csv` (per-question) and `summary.csv`
   (hierarchical accuracy with bootstrapped 95% CIs, broken down by leaf
   capability / capability group / answer format / overall) to
   `<checkpoint-dir>/eval/<dataset>/`, and prints the summary table.

## Design choices

- **Sequential, per-example generation** rather than batched — simpler and
  obviously correct, at the cost of throughput over the full test set
  (6,252 examples combined across both datasets). `--limit N` caps the
  number of test examples per dataset for a cheap sanity check before
  committing to a full run.
- **Judge on CPU by default.** Loading a second model (`Qwen/Qwen3.5-4B`)
  onto the same GPU already running the 9B model under evaluation risks
  OOM; CPU is the safe default, with `--judge-device` to override if VRAM
  allows.
- **No latency/track penalty by default.** `Evaluator.run()` supports
  enforcing per-track response-time limits (`track=Track.FRAME` → 5s max,
  per `TRACK_MAX_LATENCY`) for challenge-realistic scoring, but this script
  doesn't pass `track=`, since the goal here is measuring model *quality*
  offline, not challenge-submission latency compliance.
- **Reuses `frame_path()` via direct import** (`sys.path.insert` + `from
  build_frame_sft_dataset import ...`) instead of duplicating the path
  resolution logic — guarantees the eval script can never silently drift
  out of sync with how training data was built.

## Args

| Flag | Default | Meaning |
|---|---|---|
| `--checkpoint-dir` | required | Trained model dir from `sft_train_qwen_frame.py`. |
| `--base-model-id` | `Qwen/Qwen3.5-9B` | Base model to load before applying the LoRA adapter. |
| `--no-merge-lora` | off | Keep the adapter separate instead of merging into base weights. |
| `--datasets` | `heico` | One or more of `heico`, `lapchole`. |
| `--root-dir` | `/projects/datasets_ML/orena/` | For resolving frame paths. |
| `--output-dir` | `<checkpoint-dir>/eval` | Where `results.csv`/`summary.csv` are written. |
| `--max-new-tokens` | `32` | Generation cap. |
| `--limit` | `None` | Cap test examples per dataset, for a quick sanity check. |
| `--judge-device` | `cpu` | Device for the LLM judge. |
| `--judge-workers` | `1` | Parallel judge threads. |
