## Bug: `AttributeError: Qwen2Tokenizer has no attribute tokenizer`

### Symptom
Running `evaluate_qwen_frame.py` against an intermediate training checkpoint
(`checkpoints/Qwen3.5-9B-lora-2026-07-16_16-41-57/checkpoint-600`, an
automatic mid-training save from `--save-steps 200`, not the final
`trainer.save_model()` output) crashed inside `generate_answer()`:
```
File ".../evaluate_qwen_frame.py", line 102, in generate_answer
    answer = processor.tokenizer.decode(new_tokens, skip_special_tokens=True).strip()
AttributeError: Qwen2Tokenizer has no attribute tokenizer
```

### Root cause
`processor = AutoProcessor.from_pretrained(checkpoint_dir)` silently
degraded to a bare `Qwen2Tokenizer` instead of the full multimodal
processor. Inspecting `checkpoint-600/` confirmed why:
```
adapter_config.json  adapter_model.safetensors  chat_template.jinja
tokenizer_config.json  tokenizer.json  (+ optimizer/scheduler/trainer state)
```
No `preprocessor_config.json` — the image-processor config `AutoProcessor`
needs to build the full `Qwen3_5Processor` (tokenizer + image processor +
chat template). Without it, `AutoProcessor.from_pretrained` falls back to
loading just the tokenizer class, with no error/warning.

That file was missing because `sft_train_qwen_frame.py` constructed
`SFTTrainer` with:
```python
processing_class=processor.tokenizer,   # only the tokenizer, not the full processor
```
`Trainer` auto-saves whatever `processing_class` is at every intermediate
`--save-steps` checkpoint, so every `checkpoint-N/` only ever got the bare
tokenizer. The *final* checkpoint was unaffected, since `main()` separately
calls `processor.save_pretrained(args.output_dir)` (the real, full
processor) at the very end of training — the bug only bites when pointing
evaluation at an **intermediate** checkpoint, which is exactly what
happened here (`checkpoint-600`, not the final save).

### Fixes applied

1. **`evaluate_qwen_frame.py`** (immediate fix, works on any existing
   checkpoint without retraining): load the processor from
   `--base-model-id` instead of `checkpoint_dir`. The image
   processor/chat template never change during LoRA fine-tuning — only the
   weights (and technically the tokenizer, though not in practice here) do
   — so this is correct regardless of which checkpoint you point at.
2. **`sft_train_qwen_frame.py`** (root-cause fix, for future runs):
   `processing_class=processor.tokenizer` → `processing_class=processor`,
   so intermediate checkpoints from any *new* training run will also
   include a full, loadable processor.

Both changes are small and localized; no dataset/training-format changes
were needed since the bug was purely in what gets serialized to disk at
checkpoint time, not in how the model was trained.

### Diagnostic: raw exact-match proxy vs. real Evaluator score

Before `results.csv`/`summary.csv` finished (LLM-judge scoring is slow), a
quick manual exact-string-match analysis was run directly on
`predictions.jsonl` as a rough proxy. Comparing the two afterward:

- `open_ended`: **50.2%** (raw exact match) → **65.5%** (real, judge-scored)
  — a 15-point recovery. Confirms several "failures" in the raw check were
  genuine semantic near-misses (e.g. predicted `"Blood-soaked"` vs. gold
  `"Fully saturated"`) that the LLM judge correctly accepts as equivalent,
  not real errors.
- `number`: 47.0% → 48.8% — barely moved, as expected for a strict
  integer-equality format where exact match essentially *is* the metric.

### Concrete failure patterns found

- **`number` (counting) errors are near-miss, not random**: 63% of failures
  (445/703) are off by exactly 1. Classic VLM object-counting imprecision,
  not a training/format bug — expect this to improve only marginally with
  more training.
- **`SPATIAL_LOCALIZATION_SITUS` shows a majority-class shortcut, not real
  visual grounding.** For 5 different test questions from the same video
  (`0028 - Heico - Sigma - 9.avi`, 5 different frames/timestamps), the model
  predicted the identical answer (`"Lower left abdominal quadrant."`) despite
  the ground truth varying across 4 of the 5. Checked the training label
  distribution for this exact sub-task: only 110 examples total, and
  `"Lower left abdominal quadrant."` is the 2nd most frequent label (~25%)
  — close to a majority-class default. Since this test video's frames were
  never in training (video-level split), the constant output can't be
  memorization — it's the model falling back on a frequency prior instead of
  reading each frame, consistent with this being one of the rarest
  capabilities in the dataset (260 total training examples across 42
  videos).
- **Label inconsistency found in training data**: 13 near-duplicate
  spellings of ~6 real quadrant/pelvis answers (e.g. `"(small) pelvis."` /
  `"Small pelvis."` / `"small pelvis."`, inconsistent capitalization). Splits
  training signal across variants unnecessarily and penalizes exact-match
  scoring for no real reason.
- **No degenerate behavior otherwise**: 0 empty predictions, 0
  question-echoing, and predicted-answer length distribution (mean 6.0
  chars) almost exactly matches ground-truth length distribution (mean 6.0
  chars) — the SFT format-following (loss masked to answer-only) is working
  as intended.

### Improvement ideas discussed (not yet implemented)

1. **Canonicalize answer labels** in `build_frame_sft_dataset.py` (lowercase,
   strip trailing punctuation, merge pelvis-phrasing variants) — cheap, safe,
   directly targets the label-inconsistency finding above.
2. **Oversample rare capabilities** (esp. `SPATIAL_LOCALIZATION_SITUS`, 260
   examples vs. thousands for the dominant capabilities) via per-example
   sampling weights or row duplication in the training JSONL.
3. **Increase LoRA rank** (`--lora-r 16` → 32/64) — may be a capacity
   bottleneck for a 9B model handling ~15 sub-capabilities at once.
4. **Capability-aware batch sampling** — stratify batches so rare
   capabilities aren't left to random chance for representation.
5. **Per-capability eval logging** — currently only aggregate `eval_loss`
   and one fixed qualitative sample are tracked during training; a callback
   computing accuracy per capability at each eval step would make weak-area
   progress (or lack thereof) visible live instead of only discoverable
   after a full post-hoc evaluation like this one.
6. **Two-stage fine-tuning** — broad SFT to convergence, then a short
   lower-LR second pass oversampling only the weak capabilities.

None of these are implemented yet — logged here as the plan discussed, to
revisit once the current training run (or its early-stopped result) is
further along.

*(Update: idea 2 — "oversample rare capabilities" — was revised after
pushback. Naive per-capability duplication would replicate the existing label
skew inside that capability, potentially **reinforcing** the majority-class
shortcut rather than fixing it, and would recycle the same ~42 videos'
pixels, raising memorization risk. The corrected version is **label-balanced**
oversampling (upweight the rare answers *within* the capability, e.g.
`Upper left`: 5 examples vs `Upper right`: 30), optionally with image
augmentation — but **not horizontal flip**, which would invalidate the
left/right labels this exact capability depends on. See also the cross-dataset
finding below, which suggests part of this may be a domain-vocabulary problem
that no resampling can fix.)*

## Batched evaluation

`evaluate_qwen_frame.py` generation was rewritten from one-sample-at-a-time to
batched (`--batch-size`, default later raised to 32):

- **Left-padding** (`processor.tokenizer.padding_side = "left"`, set in
  `load_model`) — the opposite of the training collate_fn's right-padding.
  Batched decoding needs every sequence's first generated token to land at the
  same right-edge column; right-padding would misalign them. With left-padding
  the prompt boundary is a single shared column, so
  `generated[:, inputs["input_ids"].shape[1]:]` slices new tokens for the whole
  batch at once.
- `mm_token_type_ids` / multi-image `pixel_values` / `image_grid_thw` are left
  to the processor's native batched path rather than hand-rolled.
- Valid `(req, ref, path)` triples are gathered upfront (metadata only, images
  opened per-batch) so frames missing on disk are dropped *before* batching and
  can't unbalance a batch. Predictions still flush per batch.
- **Timing is now amortized per sample** (batch wall-clock ÷ batch size) — a
  batched `generate()` can't separate one sequence's latency from another's.

### Judge phase is the eval bottleneck (not generation)

Three eval jobs (12121/12122/12123) sat at 67–85 min each while *already
finished* generating — all stuck in `Evaluator.run()`'s LLM-judge scoring.
Root cause, confirmed by reading the library: `TransformersJudge.judge()`
processes **one** `(request, reference, candidate)` at a time; the
`Evaluator`'s `ThreadPoolExecutor(num_workers)` only helps for `APIJudge`
(blocking HTTP overlaps), not a local GPU/CPU model where the GIL and single
device serialize compute. There is no batched-judge entry point in the library.

Calibration: job 12120 (371 judge questions, running **alone**) took **22 min**
for its judge phase ≈ 3.5 s/question on CPU. The three concurrent jobs were
3–4× slower than that baseline purely from CPU contention on the shared node.

Fix: `--judge-device` default changed **`cpu` → `cuda`**. The 4B judge in fp32
(~16 GB) fits alongside the merged 9B model (~18 GB bf16) on one ~98 GB
RTX PRO 6000. Also: don't launch multiple eval jobs on the same node — either
run sequentially or use one job with `--datasets heico lapchole`.

## heico-only run: no early stopping, clear overfitting

Trained on heico only (7,200 rows), for the cross-dataset generalization
experiment. **Early stopping never fired** — the run completed all 3 epochs
(675/675 steps, epoch 3.0).

Why: heico-only is 7,200 ÷ 32 effective batch = 225 steps/epoch × 3 = **675
steps**, so `--eval-steps 100` produced only **7 evals**. After the best at
step 400 there were just 3 more evals (500/600/675) — one short of
`--early-stopping-patience 4`. **Patience 4 is unreachable on a 675-step run.**
If rerunning: drop patience to ~2 or use `--eval-steps 50`.

| Step | Epoch | eval_loss |
|---|---|---|
| 100 | 0.44 | 0.4317 |
| 200 | 0.89 | 0.4230 |
| 300 | 1.33 | 0.3847 |
| **400** | **1.78** | **0.3700 ← best** |
| 500 | 2.22 | 0.4616 |
| 600 | 2.67 | 0.4500 |
| 675 | 3.00 | 0.4643 |

Eval loss bottoms out at ~epoch 1.8 then rises sharply and never recovers —
**the last third of training actively hurt**. This directly answers the earlier
"are 3 epochs too many?" question: for heico-only, yes.

`best_model_checkpoint` = `checkpoint-400`. Because `load_best_model_at_end=True`
was active, `trainer.save_model()` wrote the **best** (step-400) weights to the
**top-level** dir — so point evaluation at
`checkpoints/Qwen3.5-9B-lora-heico-only/` (which also has the full
`processor_config.json`, i.e. the `processing_class=processor` fix working),
**not** at `checkpoint-675` (the overfit end-state).

## Cross-dataset ("OOD-like") result: heico-only model → lapchole test

**Overall: 41.0%** (CI 37.2–44.6%, n=2,252).

### ⚠️ `pre_evaluation SCORE` (60.3%) is an artifact here — do not use it

It reads ~19 points better than the real number. Cause: lapchole's frame track
contains **exactly one** `temporal_localization` question, which the model got
right → that bucket scores 100%. `pre_evaluation_score` averages capability-
**group** buckets *equally regardless of size*, so that single question is worth
**⅓ of the score**, alongside `aggregation` (n=955) and `object_recognition`
(n=1,296). Use `overall MEAN`.

This also corrects an earlier assumption from
[heico_data_structure.md](heico_data_structure.md): frame-track is **not**
always limited to 5 capabilities / 2 groups — lapchole has a 6th
(`temporal_localization`, n=1), and the question itself ("Does this foreign
object remain in the abdomen at the end of the procedure?") doesn't look like
temporal localization at all — likely a labeling quirk.

### By format — what transfers and what doesn't

| Format | lapchole (heico-only model) | heico (combined model, ckpt-600) |
|---|---|---|
| Multiple choice | **80.5%** | 81.9% |
| Binary | 60.7% | 77.0% |
| Open-ended | 47.7% | 65.5% |
| FO class | 38.6% | 69.9% |
| Number | 30.9% | 48.8% |

**Multiple choice transfers almost perfectly** (80.5% vs 81.9%) — a constrained
choice set doesn't depend on dataset-specific priors. Everything requiring open
generation degrades badly; `fo_class` collapses hardest.

### `SPATIAL_LOCALIZATION_SITUS`: 0.0% (n=25) — a *vocabulary* mismatch

Zero correct out of 25. Inspecting predictions vs. gold:

- **lapchole gold** = cholecystectomy anatomy: `Liver`, `Cystic duct`,
  `Cystic artery`, `Upper right abdominal quadrant`, `Left supracolic space`.
- **model predicts** = colorectal anatomy learned from heico: `Rectum`,
  `Small intestine`, `(small) pelvis`, `Lower left abdominal quadrant`,
  `Spleen`.

heico is Proctocolectomy/Rectal/Sigmoid resection (lower abdomen, colorectal);
lapchole is laparoscopic cholecystectomy (upper abdomen, gallbladder). The
model never saw `cystic duct`/`cystic artery` in training, so it **cannot**
produce them — it maps every situs question onto its heico prior. This explains
0% rather than merely low, and **reframes the earlier diagnosis**: the
`Rectum` / `Lower left abdominal quadrant` defaults spotted on heico weren't
just a majority-class shortcut, they're a **learned heico-specific prior** that
transfers catastrophically to a different procedure's anatomy.

### Caveat: the comparison is incomplete

The heico-only model's **in-distribution** score (heico test) has **not** been
run, so 41.0% (lapchole) can't be cleanly separated into "distribution shift
hurt" vs. "heico-only training is just weaker than combined training". The
62.3% reference above is a *different model on a different test set*. Next step:

## Batched eval verified end-to-end; base-model baseline (the big result)

`base_model_eval.py` was added — a thin wrapper reusing `generate_batch` /
`evaluate_dataset` from `evaluate_qwen_frame.py` verbatim, differing only in
that it loads the plain base `Qwen/Qwen3.5-9B` (no LoRA). Running it also served
as the first full end-to-end test of the **batched** generation path + GPU
judge: it completed all 2,252 lapchole examples cleanly, so batching +
left-padding + GPU judge all work.

### Base Qwen3.5-9B vs. heico-only fine-tune (r=16), both on lapchole

| Slice | Base 9B (no FT) | heico-only FT r=16 | Verdict |
|---|---|---|---|
| **Overall** | **18.1%** | **41.0%** | FT wins overall |
| `SPATIAL_LOCALIZATION_SITUS` | **56.0%** | **0.0%** | 🔴 FT destroyed it |
| `fo_class` (format) | 0.17% | 38.6% | 🟢 FT taught it |
| `object_identification` | 0.0% | (high) | 🟢 FT taught it |
| `multiple_choice` | 39.3% | 80.5% | 🟢 FT helped |
| `open_ended` | 29.3% | 47.7% | 🟢 FT helped |
| `binary` | 49.3% | 60.7% | 🟢 FT helped |

### Conclusion: catastrophic forgetting is CONFIRMED — and it's separable from format learning

Two effects happen at once, cleanly split by capability:

1. **Catastrophic forgetting (confirmed, severe).** On `SPATIAL_LOCALIZATION_SITUS`
   the *base* model scores **56%** and the fine-tune **0%**. The base predictions
   show it knows cholecystectomy anatomy from pretraining (`right upper quadrant`,
   `Gallbladder`, `common bile duct`); fine-tuning on heico **overwrote** that
   with colorectal priors (`Rectum`, `Lower left`). This proves the earlier
   hypothesis — the 0% situs on lapchole wasn't a capability the model never had,
   it's knowledge SFT *destroyed*.

2. **Format compliance (why FT still wins overall).** The base scores **0.17%**
   on `fo_class` and **0.0%** on `object_identification` — not from blindness but
   because it answers in prose ("The visible foreign objects are a clip and a
   sponge") instead of the required `"Clip, Sponge"`, so the deterministic parser
   rejects it. SFT's main value was teaching output format, which touches far
   more questions than the situs slice — hence 18% → 41% overall *despite* the
   forgetting.

**Actionable takeaway**: the goal is not "SFT vs no SFT" but "keep SFT's format
compliance without its knowledge forgetting" — i.e. lower LoRA rank, OOD-based
early stopping, KL-anchoring to base, labels-in-prompt, constrained decoding, or
SFT→GRPO (the "RL heals OOD forgetting" result). The r=8 sweep run below directly
tests the rank/forgetting tradeoff.

(As before, ignore the base model's `pre_evaluation SCORE` 0.463 — same n=1
`temporal_localization`=100% bucket artifact. Use `overall MEAN`.)

Base results stored at `orena_sft/eval_base/Qwen3.5-9B/lapchole/`.

## Checkpoint-folder collision (three runs clobbering one directory)

While the base eval ran, two *training* jobs (12140, 12146) were found writing to
the **same** `checkpoints/Qwen3.5-9B-lora-heico-only/` directory as each other
**and** as the already-completed r=16 run — because all three were launched with
the same `--run-name Qwen3.5-9B-lora-heico-only` (`--output-dir` defaults to
`checkpoints/<run_name>`).

Diagnosis evidence:
- `eval_samples.jsonl` held three interleaved step sequences appended together
  (`100..675` | `100..400` | `100 500`).
- The two live jobs were a **LoRA-rank sweep**: trainable params
  58,195,968 (**r=32**, job 12140) vs 14,548,992 (**r=8**, job 12146) — two
  different experiments mixing checkpoints, `trainer_state.json`, and
  `save_total_limit=2` rotation into one folder. Neither result recoverable.
- The top-level final adapter (mtime 14:29, 112 MB, **r=16**) was still the
  original completed run's — intact only because neither live job had hit its
  final `save_model()` yet (it would have overwritten it within minutes).

Recovery actions taken:
1. Copied the r=16 model + its preserved eval to
   `checkpoints/heico-only-r16-SAVED/` (verified: `lora_r=16`, lapchole overall
   still 41.0%). The earlier lapchole eval had already been hand-moved to
   `eval_lora1632/` inside the colliding folder, so it survived.
2. `scancel 12140 12146`.
3. Resubmitted the sweep with **distinct** run names →
   `heico-only-r32` (job 12149) and `heico-only-r8` (job 12150), each in its
   own `checkpoints/heico-only-r{32,8}/`. Also switched to
   `--eval-steps 50 --save-steps 50 --early-stopping-patience 3` so early
   stopping can actually fire on a ~675-step run (patience 4 @ eval-every-100
   was mathematically unreachable, per the heico-only finding above).

**Root-cause guard (not yet implemented, proposed):** make
`sft_train_qwen_frame.py` refuse to start (or auto-suffix the run name) if
`--output-dir` already contains a `trainer_state.json`, so a run-name collision
fails loudly instead of silently corrupting. The `Qwen3.5-9B-lora-heico-only/`
folder is now dead/corrupt — superseded by `heico-only-r16-SAVED/`; safe to
delete once the rescue copy is confirmed loadable.
