# 2026-07-21 — Direct-prompt SFT result, GRPO scoping, procedure conditioning

Followed on from the 2026-07-20 prompt-engineering work. Today: evaluated the
first prompt-conditioned SFT run, scoped GRPO against what the data actually
supports, and reframed the OOD problem around the one signal the challenge
always gives us — `procedure_type`.

Related: [2026-07-20](2026-07-20.md) (prompts.py, structured/direct, base runs),

## 1. Direct-prompt SFT: the fair comparison, and the hypothesis it kills

Trained `heico-only-9b-r16-direct` (Qwen3.5-9B, LoRA r=16/α=32, heico-only,
`--prompt-style direct`). Best checkpoint-400 (eval_loss 0.357, epoch ~1.5) —
same overfitting shape as every prior run. Evaluated **with the same
`--prompt-style direct`** (train/inference parity is enforced now).

The comparison that matters holds data, rank, and checkpoint-selection fixed and
moves **only the prompt** — `heico-only-r16` (plain) vs this run, both on
lapchole (OOD):

| | plain | direct |
|---|---|---|
| overall | 41.0% | **42.85%** |
| fo_class | 38.6% | **41.2%** |
| number | 30.9% | **33.3%** |
| **situs** | **0.0%** | **0.0%** |

Two real positives: **+1.8 overall**, and `number` *improved* (33.3 vs 30.9) —
which answers an open question from 2026-07-20 §17: **SFT on real counts
CORRECTS the base-model counting suppression** (base+direct predicted a mean
count of 0.78 vs GT 3.28; after SFT the collapse is gone). And direct SFT
(42.85%) still dwarfs base+direct (23.3%) — SFT does the heavy lifting.

### The hypothesis failed: in-context vocabulary does NOT prevent forgetting

`situs` is **still 0.0%** under direct. The premise — "put the label space in
the prompt so the model reads it instead of memorising it, and it won't forget"
— did not hold. And it was never going to, once you see why:

- `situs` asks about **anatomy** ("where is the sponge?" → "Right upper
  quadrant", "Cystic duct").
- The direct prompt injects the **foreign-object class list** (Clip, Sponge,
  Needle…).
- **Orthogonal vocabularies.** The prompt gave the model the answer space for
  `fo_class` — exactly where it helped (+2.6) — and said nothing about
  anatomical structures, so it had zero leverage on the capability that forgets.

**The injected vocabulary fixed the format problem it could reach and left the
knowledge problem untouched.** The user's read ("no meaningful difference") was
right in spirit for forgetting; the +1.8 is real but aimed at the wrong target.

### ⚠ Do NOT compare against `checkpoint-600`

That comparison (which looked like "no difference") is confounded **three ways**:
checkpoint-600 was trained on **combined** data (lapchole is in-distribution for
it, not OOD), is a **mid-training** step of a 3-epoch run, AND uses the plain
prompt. On heico both score ~0.62 — but heico is ID for both, so it cannot see
the prompt effect. Only the same-data/same-rank comparison above is valid.

## 2. `situs` is 100% open_ended — and the knowledge is *gone*, not hidden

All 25 lapchole `situs` questions are `open_ended` (LLM-judge scored). So the
0.0% is **not** a parsing artifact — the judge genuinely rejects the answers.
Predictions are the forgetting story in pure form:

| GT (cholecystectomy) | pred (colorectal) |
|---|---|
| Cystic duct | Ureter |
| Liver | Small intestine / Rectum |
| Upper right quadrant | Lower left quadrant / (small) pelvis |
| cystic duct, cystic artery | Sigmoid colon, small intestine |

Every prediction is anatomically coherent for the **wrong procedure**.

**The decisive measurement**: across ALL 2,252 lapchole predictions, the model
produces cholecystectomy anatomy **zero times** — `gallbladder` 0, `cystic` 0,
`liver` 0, `hepatic` 0, `upper right` 0. Of the 25 situs answers: 0
cholecystectomy, 16 explicitly colorectal. **The correct vocabulary has ~zero
probability mass in the policy.** The base model had it (situs 56% before SFT);
SFT collapsed `P(anatomy | procedure)` onto `P(anatomy | heico)`.

## 3. GRPO: verified feasible, scoped to what the rewards support

Checked the installed stack: **TRL 1.8.0 has native VLM GRPO**
(`GRPOTrainer` reads images from `{"type":"image",...}` prompt parts — exactly
our JSONL shape). Reward contract:
`reward_func(prompts, completions, completion_ids, **reward_kwargs)`, where
`reward_kwargs` carries **every extra dataset column** — so `answer` and
`format` flow straight through. `vllm` is **not installed** (generation will be
the bottleneck at G rollouts).

### Scope: verifiable formats only

`fo_class` (920) + `number` (768) + `binary` (176) = **~83% of lapchole** test
questions, all scored by deterministic parsers, **no judge in the loop**. Do NOT
put the judge in rollouts — `TransformersJudge` is 3.5 s/question with no batch
path; fatal at G samples/prompt.

Reward design: `reward_exact` (the Evaluator's own `read()`+`compare()`, so
training can't diverge from scoring); `reward_count_shaped` for `number`
(`max(0, 1−|pred−gt|/3)` — **the main reason to do GRPO**: 63% of counting
errors are off-by-one, where cross-entropy gives no gradient); `reward_parses`
(small, anti-drift). All return 0.0 on `ValueError`, never raise. **Validate
rewards offline against an existing results.csv before any GPU.**

### The risk: advantage collapse (the user flagged it)

GRPO's signal *is* within-group reward variance. The SFT model's entropy fell
across training:

| epoch | eval_entropy |
|---|---|
| 0.44 | 0.407 |
| 0.67 | 0.287 |
| **1.56 (best)** | **~0.22** |
| 2.44 | 0.170 |

**Refined framing** (the key correction): diversity only matters where the model
is confident *and wrong*. Confident+right (most fo_class/binary) → zero
advantage is *correct*, nothing to learn. The danger is confident+wrong,
especially counting. Levers that buy diversity **without a worse init** (do NOT
GRPO from base — it relearns format SFT already taught):

1. **Temperature at rollout** (1.0–1.2) — primary knob, decoupled from init.
2. **Init from an earlier SFT checkpoint** (epoch ~0.7–1.0, entropy ~0.25–0.29,
   format already learned) — the nuanced middle path.
3. **Filter to mixed-correctness prompts** (dynamic sampling / DAPO) —
   guarantees every step has signal.

**Pre-flight before training**: sample G=8 at temperature over ~500 prompts from
the SFT checkpoint, measure the **fraction of zero-variance groups**. <40% → fine;
70%+ → apply lever 2/3 first. Reuses existing generation code, no trainer.

### GRPO CANNOT fix situs (important boundary)

`situs` is open_ended → **not** in the verifiable-reward set. Worse: even with a
judge in the loop, GRPO starts from the already-collapsed checkpoint where
`cystic duct` has ~zero mass (§2). **GRPO amplifies what the policy already
samples; it cannot inject a token the model never emits.** All G rollouts are
wrong colorectal answers → a perfect judge scores them all 0 → zero variance,
zero gradient. Temperature can't rescue a token with ~0 logit mass. So:
**data first, then RL** — get cholecystectomy anatomy back into the sampling
distribution (anti-forgetting or public Cholec data), *then* a judge reward can
reinforce it. RL sharpens a distribution; it doesn't create missing modes.

## 4. The OOD reframe: condition on procedure, don't chase datasets

User's sharp objection: adding lapchole data makes lapchole ID, but the official
test is "mixed, **unseen** procedures" — procedure #3 (appendectomy, hernia…)
stays broken. Adding a second procedure gives two priors, not a fix.

**The reframe that makes it tractable**: `procedure_type` is on every `Request`
(and every official test case). You never guess the procedure — you're *told* it.
The failure isn't missing knowledge; the base model knew cholecystectomy anatomy
(56% situs). SFT **collapsed the conditional** `P(anatomy | procedure)` onto one
branch. So robustness to unknown procedures = two levers, neither needing to know
the test set:

1. **Preserve the base model's broad pretrained anatomy** — anti-forgetting
   (low rank: r=8 kept 17.9% vs r=16's 0%; KL-anchor; OOD-based stopping). The
   base already spans arbitrary procedures; the job is *not erasing* that.
2. **Condition on `procedure_type`** (currently unused) so the model selects the
   right anatomical frame. Procedure diversity in training then teaches
   *conditioning as a skill*, which is what extrapolates to procedure #3.

**Testable with existing data**: heico is 3 sub-procedures (Procto/Rectal/Sigmoid;
heico *test* is all Sigmoid). Train on Procto+Rectal(+lapchole), hold out Sigmoid
as a genuine unseen-procedure test. If conditioning generalises to held-out
Sigmoid, it should generalise to their unknowns — measured, not hoped.

## 5. Implemented: `--condition-procedure` in `base_model_eval.py`

Prepends `Procedure type: <name>.\n` to each question, from `req.procedure_type`.

- **Injected in the USER turn, not the system prompt** — composes with any
  `--prompt-style` (plain included), leaves `prompts.py` untouched, mirrors how
  the challenge supplies metadata (alongside the question).
- Raw question still logged to `predictions.jsonl`; only what the model sees
  changes.
- Output dir gets a `_conditioned` suffix.
- Verified: renders as `…<|vision_end|>Procedure type: Laparoscopic
  Cholecystectomy.\n<question>…` — the line lands after the image, before the
  question.

**Running now** (both writing to distinct dirs, no collision, but contending on
gpu38): job **12358** = direct+conditioned, job **12359** = plain+conditioned.

**Expectation to calibrate against**: for the BASE model, conditioning should be
~neutral — it isn't confused about the procedure (situs already 56% unconditioned).
A flat result is the *expected* shape, not a failure. The one interesting cell is
whether direct+conditioned recovers situs from direct's 46.4% back toward the
unconditioned 56.0% (direct's FO-class framing had pulled it down). The real
payoff only appears **post-SFT**, where the model has a *collapsed* prior to
override — this run just confirms conditioning doesn't hurt and the base can read
the signal at all. NOT yet wired into `sft_train_qwen_frame.py` /
`evaluate_qwen_frame.py` — needed for the actual experiment, same parity
discipline as `--prompt-style`.

## 6. Three ideas evaluated (base-model results + probing data)

- **DINOv3 + projector + LLM (LLaVA-style, C2): don't build.** Pulled the probing
  results (`Orena_probing/results/probe_results.csv`): DINOv3 IS the best encoder
  on average (mean balanced-acc 0.565 vs Qwen 0.500, CLIP 0.412), strongest on
  fo_class (0.644/0.735). BUT `object_count` is at **chance for every encoder**
  (0.247, 4 classes) — because the probe pools features (CLS/mean) into one
  Linear, and counting can't be linearly decoded from a pooled vector. So there
  is **no evidence DINOv3 helps counting**, and building a projector needs
  caption-scale alignment data we don't have (VQA-only, ~20k pairs). *The real
  idea hiding here*: re-probe DINOv3 **dense** patch features with a counting
  head — a ~1-day experiment reusing `Orena_probing/` that decides whether a
  counting specialist is viable. Deployable form = route counting to a
  specialist, keep Qwen for the rest.
- **GRPO on verifiable formats: highest value** (§3). Counting is the app —
  dense reward where SFT's cross-entropy gives none. Zero inference cost.
- **Rationale distillation: hold.** Teachers aren't better than the student
  (27B/31B = 42.1/39.4% vs 9B 41.0%). Rejection sampling filters the *answer*,
  not the *reasoning* — qID 17751's correct-count trace cited a coordinate on the
  instrument shaft, not the clip (right answer, spurious rationale). And STaR ≈
  poor-man's GRPO on the same signal — largely subsumed by §3.

# Part III — GRPO implemented and smoke-tested (`orena_grpo/grpo.py`)

## 7. The script

Built the full GRPO trainer. **Reward = the FOCUS Evaluator's own correctness**,
so the training signal can't diverge from the leaderboard metric:
- closed formats → `get_format_class(fmt)().read()`+`compare()` (identical to
  `Evaluator.run()`);
- open formats → `focus.evaluation.judges.APIJudge` with the **same**
  `build_judge_prompt` the Evaluator uses, backed by an OpenAI model.
`extract_answer` is applied first (so `"yes."` → `yes` scores).

**Two levers, both `--flag/--no-flag`:**
- `--init-from-sft` — warm-start merges the SFT adapter into base, trains a fresh
  GRPO LoRA on top; cold-start uses plain base. TRL derives the KL reference by
  disabling the trainable adapter, so the anchor is automatically merged-SFT
  (warm) or base (cold) — exactly right for each.
- `--use-kl` — sets `beta` (0.04) or 0.

Verified against TRL 1.8.0 before writing: native VLM GRPO exists; reward gets
every dataset column via `reward_kwargs` (needs `remove_unused_columns=False`);
`_is_vlm=True` when a processor is passed; images are read from
`{"type":"image",...}` parts of the `prompt` messages (dataset uses
`with_transform` for lazy PIL loading). Combined data, `--group-size 10`, direct
prompt, loaded from `FocusDataset` so the judge gets real
`start_time`/`procedure_type`.

**wandb + rollout inspection**: TRL already logs `reward`, `reward_std`,
**`frac_reward_zero_std`** (the advantage-collapse metric), `kl`, `entropy`. Added
a `RolloutRecorder` + `RolloutInspectionCallback` that every N steps prints one
group (question, GT, each completion + reward) — surfaces the *highest-variance*
group, i.e. where learning happens.

## 8. Bug (recurring root cause): TRL left `<think>` open

First smoke run was **mechanically fine but scientifically broken** — every
completion was reasoning (`"1. **Scan the image for clips:**"`),
`clipped_ratio=1`, `mean_terminated_length=0`, **reward 0 at every step,
frac_reward_zero_std=1**. TRL renders the generation prompt **without**
`enable_thinking=False`, so Qwen's `<think>` block is left OPEN and the
direct-SFT model (trained with the empty CLOSED block) reverts to reasoning,
then gets cut at 32 tokens before any answer.

**Fix**: `GRPOConfig(chat_template_kwargs={"enable_thinking": False})` — verified
TRL forwards it to `apply_chat_template` at generation. Same enable_thinking root
cause as the base-Gemma saga (2026-07-20), now in TRL's generation path. Also
removed an explicit `step=` in the callback's `wandb.log` that fought TRL's step
counter ("Tried to log to step 2 < current step 15" → table dropped).

## 9. Healthy smoke run — signal confirmed, shaping opportunities visible

After the fix: terse answers, `clipped_ratio=0`, `reward` swinging 0.1–0.95,
`reward_std ~0.5`, `frac_reward_zero_std` mostly 0, `kl` ~1e-4. **GRPO has
signal.** The group prints show exactly where the reward is dense vs sparse:

- **Counting (GT `6`, rollouts `4,5,6,7,8`)**: only the `6`s score; `5`/`7` are
  near-misses thrown away. → the case for a **count-shaped reward**
  (`max(0, 1−|pred−gt|/3)`). Counting is the worst format and GRPO's best chance,
  and exact-match leaves most of the signal on the floor.
- **`fo_class` combos (GT `Clip, Specimen`)**: 1/10 got both; the rest said one
  class and scored 0. Set-equality is all-or-nothing → an **F1-over-set** reward
  would give partial credit and push toward completeness.

Both were flagged in the plan (§3); the rollouts now justify them empirically.
Kept as opt-in (`--shape-counting`, `--shape-fo-f1`, not yet implemented) so the
faithful Evaluator reward stays default for A/B.

## 10. Run scale, config, and mechanics

Moved script to `orena_grpo/` (fixed imports to reach `orena_sft/` helpers; SFT
checkpoints stay in `orena_sft/checkpoints`, GRPO output in
`orena_grpo/checkpoints`). Added `orena_grpo/grpo.slurm` (h200).

**Prompt counts** (combined TRAIN, frames exist): **13,748** total, of which
**1,962** open (judge) formats → **11,786** verifiable-only.

**Steps** (defaults per_device 20, grad_accum 4, G=10 → 8 prompts/step, 1 epoch):
full **1,719** steps, verifiable **1,474**. At ~50 s/step (grad_accum 4) that is
**~20–24 h — will NOT finish one epoch in the Slurm window**. GRPO rarely needs a
full epoch; **cap with `--max-steps` (~400 ≈ 5–6 h)** and watch the reward curve.

**Batch size**: must be a multiple of `--group-size`. **32 is invalid with
G=10** (script errors; TRL's global-batch check fails too). Use 30 or **40**;
batch 40 fits the H200 (batch 20 ran with headroom) and, with grad_accum 2, gives
the same 8 prompts/step at ~half the wall-clock — directly helps the time budget.

**Mechanics** (as configured): reward ∈ {0,1} per completion; **advantage =
group z-score** `A_i = (r_i − mean)/std` over the G=10 completions (`scale_rewards
=True`) — the group mean is the baseline, no critic; loss = clipped policy
gradient + `beta·KL(π‖π_ref)`, `num_iterations=1` (on-policy). Zero-variance
groups → zero advantage → no gradient (= `frac_reward_zero_std`).

## 11. Launch commands

Verifiable-only smoke (no OpenAI key), first — confirms memory + the loop:
```bash
sbatch --export=ALL,EXTRA_ARGS="--init-from-sft --use-kl --skip-open-formats \
  --group-size 10 --batch-size 20 --grad-accum 1 --max-steps 10 --rollout-log-steps 2" \
  orena_grpo/grpo.slurm
```

Real verifiable-only run (~400 steps, batch 40):
```bash
sbatch --export=ALL,EXTRA_ARGS="--init-from-sft --use-kl --skip-open-formats \
  --group-size 10 --batch-size 40 --grad-accum 2 --max-steps 400" \
  orena_grpo/grpo.slurm
```

Full run with the OpenAI judge (key in the SAME --export token, no space after
commas):
```bash
sbatch --export=ALL,OPENAI_API_KEY=sk-...,EXTRA_ARGS="--init-from-sft --use-kl \
  --judge-model gpt-4o-mini --group-size 10 --batch-size 40 --grad-accum 2 --max-steps 400" \
  orena_grpo/grpo.slurm
```
Cold-start ablation: `--no-init-from-sft`. No-KL: `--no-use-kl`.
