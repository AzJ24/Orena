| Qwen | Gemma | Purpose |

### Architecture differences — all verified empirically against the real model

Nothing here was assumed from the Qwen script; each was checked before writing:

1. **Model class**: `Gemma4ForConditionalGeneration` (processor `Gemma4Processor`).
2. **Assistant marker for loss masking**: `"<|turn>model\n"`. Gemma renders an
   already-answered turn as `<|turn>model\n{answer}<turn|>` with **no** thinking
   block for a plain-text answer (contrast Qwen, which emits an empty
   `<think></think>`). Verified the prompt-prefix tokenization is an exact
   prefix of the full tokenization, so slicing at the marker masks exactly the
   prompt.
3. **Image tensors**: processor returns `pixel_values` (n, 2520, 768) +
   `image_position_ids` (n, 2520, 2) — fixed soft-token size per image,
   concatenated along dim 0. There is **no `image_grid_thw`** (Qwen-specific).
4. **`mm_token_type_ids`**: Gemma also returns/requires it (0 = text, 1 = image),
   same as Qwen — propagated and padded with 0.
5. **Batched images (eval)**: Gemma's processor requires a **nested** per-text
   list `[[img0], [img1], …]`; Qwen's flat `[img0, img1, …]` raises
   *"Received inconsistently sized batches of images and text."*

Collate function verified end-to-end without loading 31B weights: correct
batch shapes, right-padding, and loss masking (target = `'Clip, Sponge<turn|>\n'`
only, prompt+image fully masked).

## 2. Bug: LoRA on `Gemma4ClippableLinear`

First smoke test (job 12291) crashed:
```
ValueError: Target module Gemma4ClippableLinear(...) is not supported.
Currently, only ... torch.nn.Linear ... are supported.
```
**Cause**: the Qwen-style `target_modules=["q_proj", …, "down_proj"]` is matched
by *suffix across the whole model*. Gemma's **vision tower reuses those same
names** but wraps them in `Gemma4ClippableLinear` (not plain `nn.Linear`), which
PEFT can't adapt.

**Fix**: scope LoRA to the language model via regex
`r".*language_model.*\.(q_proj|k_proj|v_proj|o_proj|gate_proj|up_proj|down_proj)"`
— verified to match **410 plain-Linear text projections, 0 vision modules**, and
`get_peft_model` then succeeds (61,214,720 trainable params, 0.195%).

**Side finding — Qwen was always language-model-only too.** Checked Qwen's
architecture: its `target_modules` matched **128 text modules, 0 vision**,
because Qwen's ViT names its projections `qkv`/`proj`/`linear_fc1`/`linear_fc2`
— no overlap. So Qwen's LoRA was implicitly text-only by naming accident; the
Gemma regex makes the same behavior explicit. The two are consistent.

## 3. Bug (mine): the `enable_thinking` mistake

I originally set the Gemma generation prompt to
`add_generation_prompt=True, enable_thinking=True`, claiming the flag was
"inverted vs Qwen". **That was wrong**, and the user caught it from the log.

I had "verified" it by printing only the **last 45 characters** of the rendered
prompt. The tail looked clean (`<|turn>model\n`), but I missed that
`enable_thinking=True` **injects a `<|turn>system\n<|think|>\n<turn|>` block at
the head** — which is precisely what turns thinking ON. The model then dutifully
generated `thought\nThinking Process:\n\n1. **Analyze the Request:** …`.

Full picture (Gemma):
- `enable_thinking=True` → injects `<|think|>` **system prompt** → thinking ON.
- default / `enable_thinking=False` → opens a `<|channel>thought` **tail** → thinking ON.
- **Neither** gives a thinking-free prompt.

**Fix**: a `build_generation_prompt()` helper that renders the user turn with
`add_generation_prompt=False` and appends `"<|turn>model\n"`. Verified byte-
identical to truncating the *training* render at the marker, and contains no
`<|think|>` / no thought channel. Applied to all three Gemma generation sites
(`preview_example`, `SampleGenerationCallback`, `evaluate_gemma_frame.generate_batch`;
`gemma_eval_base.py` inherits it).

**Qwen re-checked and is correct** — its `enable_thinking=False` prompt is
byte-identical to its training render truncated at the marker (empty closed
`<think></think>`, no injected system). The two model families genuinely differ
here; Qwen needed no change.

**Lesson**: verifying a rendered prompt by its tail is not verification. Print
the whole string.

## 4. New feature: `preview_example()` startup print

Added to **both** train scripts, called once before `trainer.train()`. Prints, for
one eval example: the full rendered chat (system/user/model turns), the
ground-truth target, the generation prompt, and a **live greedy generation** from
current weights. Per-model correct flags (Gemma: `build_generation_prompt()`;

It immediately earned its keep: the pre-training preview showed base Gemma
generating `'thought\nnone'` **even with the clean prompt** — revealing that
Gemma's thinking reflex lives in the **weights**, not just the template.

### Catastrophic forgetting reproduced at 31B

`spatial_localization_situs` drops **53.6% → 22.6%** after heico-only SFT —
the same knowledge-destruction pattern found with Qwen (56% → 0%), where
cholecystectomy anatomy is overwritten by heico's colorectal priors. Gemma
**retained more** than Qwen did (22.6% vs 0.0%).

### ⚠️ The base number (6.1%) is NOT a fair knowledge baseline

Base Gemma scores **exactly 0.0% on every deterministic-parse format**
(`binary`, `fo_class`, `number`) but 57.6% on `multiple_choice` and 30.2% on
`open_ended`. That split is the tell — it's a **parsing/format artifact**, not
ignorance:

- **100% of base predictions (1216/1216) begin with `thought`** — the reflex is
  in the weights, unaffected by our clean prompt.
- **~30% are truncated mid-thought** (no terminal punctuation) because
  `--max-new-tokens 32` is consumed by the thinking block, so the model **never
  reaches its answer**, e.g.
  `'thought\nI cannot identify any surgical foreign objects… If you are concerned about'`.
- When it does finish, it answers in **prose** —
  `'thought\nThe surgical foreign object visible in this image is a surgical clip.'`
  for GT `'Clip'` — semantically right, but the strict parser scores it wrong.
- `multiple_choice` (constrained) and `open_ended` (LLM judge tolerates
  paraphrase) survive, which is exactly why only those two are non-zero.

**So the base-vs-trained gap here mostly measures format compliance**, the main
thing SFT teaches — consistent with the base-Qwen finding (`fo_class` 0.17%,
`object_identification` 0.0%). To get a fair base baseline one would need to
raise `--max-new-tokens` (e.g. 256) so it finishes thinking *and* answers, then
strip the thought block before scoring. **Not yet implemented.**

(As always: ignore `pre_evaluation SCORE` — still inflated by the n=1
`temporal_localization`=100% bucket.)

## 8. Correction #2: Google's official guidance (my §3 "fix" was also wrong)

The user supplied Google's documented usage for `gemma-4-31B-it`, which
overturned the §3 conclusion. Google's snippet + the model card's "Thinking Mode
Configuration" section state:

- Thinking is triggered by a `<|think|>` token **at the start of the system
  prompt**; remove it to disable.
- Thinking **ON** → `<|channel>thought\n[reasoning]<channel|>` then the answer.
- Thinking **OFF** → the model still emits the tags but with an **empty** block:
  `<|channel>thought\n<channel|>[Final answer]`.

**What I got wrong.** In §3 I read `<|channel>thought\n<channel|>` as *opening* a
thought channel and concluded `enable_thinking=False` also enabled thinking. It
does not: `<|channel>` opens and `<channel|>` closes, so that string is an
**empty, CLOSED** thought block — exactly analogous to Qwen's `<think>\n\n</think>`
— i.e. thinking **OFF**, pre-filled for the model so it starts directly on the
answer. `enable_thinking=False` was correct all along.

Worse, my §3 "fix" (bare `<|turn>model\n`) is structurally the *thinking-ON*
prompt minus the system token: with no pre-filled empty block and no `<|think|>`,
base Gemma had **no "thinking is done" signal** and generated its own
`thought\n…`. That is precisely the 100%-thought-prefix pathology in §6.

Verified renderings:

| flag | rendered prompt |
|---|---|
| `enable_thinking=False` | `<bos><\|turn>user\n…<turn\|>\n<\|turn>model\n<\|channel>thought\n<channel\|>` |
| `enable_thinking=True` | `<bos><\|turn>system\n<\|think\|>\n<turn\|>\n<\|turn>user\n…<turn\|>\n<\|turn>model\n` |

**`processor.parse_response()`** (which I hadn't found) is the proper answer to
the parsing problem — it returns `{"thinking": ..., "content": ...}` and strips
`<turn|>`, for both modes:

```
'<|channel>thought\nLet me look. I see metal clips…<channel|>Clip, Sponge<turn|>'
  -> {'thinking': 'Let me look. I see metal clips…', 'content': 'Clip, Sponge'}
'<|channel>thought\n<channel|>Clip, Sponge<turn|>'
  -> {'thinking': '', 'content': 'Clip, Sponge'}
```

### `gemma_eval_base.py` rewritten to Google's pattern

| | before | after |
|---|---|---|
| model class | `Gemma4ForConditionalGeneration` | `AutoModelForMultimodalLM`, `dtype="auto"` |
| prompt | hand-built user-render + `<\|turn>model\n` | `apply_chat_template(tokenize=True, return_dict=True, add_generation_prompt=True, enable_thinking=False)` — one call, handles the image |
| decode | `skip_special_tokens=True` | `skip_special_tokens=False` |
| answer | raw text (kept `thought…`) | `parse_response()["content"]` |
| `max_new_tokens` | 32 | 128 |

**Result: `thought` prefix went 100% → 0%**, `thinking` field empty, and
`pred_answer` contains no `<turn|>` (0/50 checked). A `raw_response` field was
added for debugging — the `<turn|>` visible there is intentional
(`skip_special_tokens=False`), not a bug; the *scored* field is `pred_answer`.

**Lesson (again, sharper):** the §3 error and this one share a root cause — I
inferred template semantics from partial output instead of reading the model's
own documentation. Check the model card first.

Fixing the prose wrapper alone raises the ceiling **5.5% → 18.0%**. The dominant
problem is that **nothing tells the model the answer must come from a closed
set** — it answers `surgical instrument`, `a probe`, `a cyst`. Top outputs:

```
168×  'the foreign objects visible in this image are:\n- surgical instrument'
 89×  'the foreign object classes visible in this frame are: surgical…'
 69×  'the surgical foreign object visible in this image is a surgical…'
```

### Proposed prompt changes (not yet implemented)

1. **Inject the closed label set** — "Valid classes are exactly: Clip, External
   drain, Gallstone, Needle, Silicone loop, Specimen, Specimen bag, Sponge. Use
   ONLY these names, never a generic term like 'surgical instrument'."
2. **Demand bare output** — "Answer with ONLY the value, no sentence."
   (per-format: class names / a single integer / one listed option)
3. **A system prompt** killing the detection framing (the base script currently
   sends none) — the "no bounding box detections" phrasing suggests the model
   thinks it's a detection API.
4. **One-shot example** in the exact target format.

**The experiment this enables**: SFT bought ~+25 points *mostly by teaching
format*, at the cost of catastrophic forgetting. If prompting recovers that
format gap, you get compliance **without** the forgetting. Clean design is a
**2×2** — {base, fine-tuned} × {plain, structured prompt} — which directly asks
"is SFT needed here, or just a better prompt?"

  Verified `apply_chat_template` accepts a **list of conversations**, batches all

  with varied image sizes/prompt lengths. Also set `padding_side="left"` and
  moved the missing-frame filter before batching.

# Part II — Prompt engineering (§9 implemented)

## 12. `prompts.py` — the structured prompt

New shared module, used by both base-eval scripts. Three constraints drove it:

1. **Format-agnostic.** `Request` carries **no answer format** — `_format` lives
   only on the ground-truth `Reference`. A prompt branching on it would work
   offline and be impossible at submission. So there is ONE prompt, keying off
   the question's own wording ("how many", "yes or no", the listed options).
2. **CoT without `enable_thinking`.** Reasoning is a plain `REASONING:` line in
   the visible output, `extract_answer()` keeps only the `ANSWER:` line. Behaves
   identically on Qwen and Gemma, independent of either thinking machinery.
3. **OOD-safe.** No anatomy, procedure, or dataset vocabulary. The one closed
   vocabulary is the challenge's own FO registry, read live from
   `FOType.names()`.

**The registry has 10 classes, not the 8 in §9** — §9's list was derived from
observed heico labels; the registry adds `Mesh` and `Absorbable Hemostatic
Agent`, and `focus.foreign_objects` states more arrive as metadata in the test
phase, which a dynamic list picks up for free. `FO_DEFINITIONS_FILE`'s docstring
explicitly sanctions reading it at inference.

Answer rules mirror the parsers exactly: `Binary.verify` rejects `"Yes."`,
`Number.verify` is `.isdigit()`, `FOClass` takes registry names or a lone
`none`.

A second style, **`direct`**, was added later: byte-identical to `structured`
except it drops the REASONING line. Comparing the two isolates the value of
reasoning out loud with nothing else moving.

## 14. The prompt SUPPRESSES detection (the important finding)

Same 24 counting questions:

| run | mean predicted count | correct digit | says 0/none |
|---|---|---|---|
| **ground truth** | **3.12** | — | — |
| plain | 1.42 | **7/24** | 1/24 |
| structured v1 | 0.33 | 1/24 | 19/24 |
| structured v2 | 0.46 | 2/24 | 17/24 |
| native thinking | 1.83 | **8/24** | 0/24 |

The structured prompt makes the model **3.5× worse at seeing objects**. The
rejections are near-verbatim: *"The image shows surgical instruments (graspers)
manipulating tissue, but no foreign objects **from the specified list** are
present."*

**Diagnosis**: the injected `FO_DEFINITION` leads with exclusions ("standard
surgical instruments … are not considered foreign objects"), and the model
over-applies it, sweeping real clips into the "instruments" bucket. Guarding
against over-counting, it induced catastrophic *under*-counting — in a model
that was **already** under-counting (1.42 vs 3.12). The exclusion rule pushes
in exactly the wrong direction.

Caveat: plain→structured changes three things at once (definition, class list,
response shape), so blame is not yet attributed. The recited phrase points at
the **list** as much as the definition. **The names-only ablation is unrun.**

### Case study: qID 17751 — the two failure modes are orthogonal

| | structured (no thinking) | native thinking |
|---|---|---|
| Output | `ANSWER: 0` | `I can see 1 Clip in this image.` |
| Format | ✅ parses | ❌ `.isdigit()` rejects |
| Perception | ❌ "no clips visible" | ✅ correct (GT=1) |
| Time | 0.33 s | 5.41 s |

Both scored wrong, for opposite reasons. The thinking trace runs a real search
(emitting `{"point": [500, 823], "label": "Clip"}`); the structured REASONING is
a **post-hoc justification of an already-decided answer**. Inspecting the frame:
a small metallic clip sits at the instrument tip, but the model's cited point
lands on the instrument *shaft* — so its correct "1" may be partly prior, not
grounding. Don't over-credit the 33%.

## 15. Qwen `base_model_eval.py` rewritten self-standing

No longer imports from `evaluate_qwen_frame.py`. Built on the canonical
documented snippet (`AutoModelForMultimodalLM`, one `apply_chat_template
(tokenize=True, return_dict=True)` call). Three Qwen specifics, each verified
rather than ported by analogy from Gemma:

1. **`parse_response()` exists but RAISES** — `hasattr` is True, calling it
   throws *"This tokenizer does not have a `response_schema`"*. Qwen ships no
   schema where Gemma does. Hand-rolled `strip_thinking()` instead.
   **Attribute presence is not capability.**
2. **`padding=True` is REQUIRED** for batching (via `processor_kwargs`). Without
   it a ragged batch raises. **Two prompts of identical length slip through** —
   my first test accidentally used two such prompts and looked clean.
3. `enable_thinking` semantics match Gemma's with different tokens: `False` →
   empty *closed* `<think>\n\n</think>`; `True` → `<think>\n` left open.

## 16. Bug (mine): the 300-CHARACTER limit, not tokens

The rewritten script scored **14.1%** vs v0's **18.1%** on plain lapchole. Cause:
I changed `--max-new-tokens` 32 → 128.

- Deterministic formats are **identical to 16 decimal places** (binary
  `0.49250440917107585`, number `0.24436973608475038`); 1731/2252 predictions
  byte-identical. The model did not change.
- Judged formats exploded in length: open_ended 98.6 → **320.8 chars**,
  multiple_choice 109 → 359.

`OpenEnded.verify` **raises above 300 characters**, and `MultipleChoice`
inherits it:

| judged answers | n | accuracy |
|---|---|---|
| >300 chars | 234 | **0.0%** |
| ≤300 chars | 154 | 26.0% |

**v0's 18.1% was flattered by truncation** — the 32-token cap accidentally
enforced the scorer's length rule. Neither number reflects capability.

Two lessons: (a) **raising `max_new_tokens` on a prose-generating model LOWERS
the score**; 256 would have been worse still (176/388 answers were *already*
being cut at the 128-token ceiling). (b) The failure is **invisible in the
metrics** — `Evaluator` catches the `ValueError` and records "incorrect", so a
length disqualification looks identical to a wrong answer. Check answer lengths
whenever a judged-format score looks oddly low.

## 18. `--enable-thinking` + `direct` is broken (unusable run)

- `</think>` appears in only **67/128 (52%)** of generations; `<think>` in 0/128
  (correct — the opening tag is in the prompt).
- Raw length median 3,541 chars, **max 4,223** = the 1024-token ceiling. Half
  the questions are still deliberating when generation stops.
- 61/128 empty `thinking`, 14/128 empty `pred_answer`.

**`max_new_tokens` is a guillotine, not a reasoning budget.** Nothing forces the
model to close `</think>` and answer. Worse, `extract_answer`'s fallback then
takes the *last non-empty line* of an unfinished thought and returns a fragment
(`'Is there an absorbable hemost'`) or empty (markdown bullets strip to nothing)
— **a truncated failure is dressed up as a confident wrong answer**.

Fix proposed, not yet implemented: **budget forcing** (s1-style) — generate to a
think budget, then append `</think>` (single token `248069`) for rows that
haven't closed and generate a short answer continuation. Every question then
gets an answer and latency becomes bounded and tunable. Plus: `extract_answer`
must return empty on unterminated output, and `predictions.jsonl` should carry a
`truncated` flag.

Also a design conflict: `direct` says *"no reasoning"* while the template forces
an open think block. The two halves fight.

## 19. Training + eval made prompt-style aware

`sft_train_qwen_frame.py` and `evaluate_qwen_frame.py` both take
`--prompt-style {plain,direct,structured}` + `--fo-definitions`. `plain` is
byte-identical to every previous run.

- A `with_system()` helper is used at **all three** render sites (collator,
  `SampleGenerationCallback`, `preview_example`) so they cannot drift.
- **`structured` is refused at training time**: every target is a bare answer,
  so training on it would teach the model to *disobey* its own prompt. It needs
  rejection-sampled reasoning traces (a STaR-style project). `direct` matches
  the existing targets exactly — which is why it is the only trainable style.
- Verified against the real processor:

| style | tokens | prompt | target | exact prefix | train prompt == eval prompt |
|---|---|---|---|---|---|
| plain | 552 | 546 | 6 | ✅ | ✅ |
| direct | 952 | 946 | 6 | ✅ | ✅ |

The system turn sits before `ASSISTANT_MARKER`, so it is masked out of the loss
like the rest of the prompt; the target stays `'Clip, Silicone loop<|im_end|>\n'`.
Sequence length grows **+72%**, so batch/grad-accum need rebalancing (16×2 →
8×4) — unmeasured, worth a `--max-steps 20` calibration first.

**Hypothesis under test**: with the class vocabulary *in context*, the model can
read the label space instead of memorising it, so heico's colorectal prior has
less reason to overwrite pretrained anatomy. Measurement is
`spatial_localization_situs` on lapchole. Watch also whether SFT *corrects* the
§14/§17 counting suppression — ground-truth counts directly contradict it.

`import sys`. Compiling is not verifying.
